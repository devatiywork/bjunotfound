1) Таблица categories — категории продуктов (админ заполняет)
Зачем

Чтобы не хранить строку “Молочные продукты” в каждом продукте, а хранить ссылку category_id.
Поля:
1. id — PK, внутренний ID категории.
2. parent_id (nullable) — если хочешь дерево категорий (например “Молочные” → “Йогурты”).
3. name* — название категории (на одном языке, например на русском).
4. slug* — строковый ключ (“dairy”, “yogurt”), удобно для URL/фронта.
5. is_active — включена ли категория (чтобы скрывать без удаления).
6. created_at / updated_at — служебные даты.

 Реализация системы блюд

 1) Таблица dishes — “Блюдо” (карточка)

Назначение: хранит только “шапку” блюда. Никаких вычислений.

Поля:
id — внутренний ID блюда.
user_id — владелец блюда.
name — название блюда (например “Омлет с сыром”).
description (nullable) — текстовое описание (свободный текст).
portions — количество порций блюда (целое > 0).
is_archived (default false) — мягкое скрытие/архивирование (удобно для будущего планирования и истории).
created_at, updated_at.

Важно:
portions нельзя делать 0 — иначе деление на ноль.

Название лучше индексировать по (user_id, name) для быстрых поисков.

2) Таблица dish_items — состав блюда (ингредиенты)

Назначение: фиксирует, какие продукты входят в блюдо и “как пользователь их задал” (граммы/мл/порции).

2.1. Общие поля

id — внутренний ID строки.
dish_id — ссылка на dishes.id.
product_user_id — ссылка на пользовательский продукт (тот, где есть КБЖУ на 100г и покупки).
sort_order — порядок отображения (0..n).
note (nullable) — комментарий (“без кожи”, “после жарки”, “сырой вес” и т.д.).

2.2. Тип измерения

measure_type — ENUM:
GRAMS — ингредиент задан в граммах
MILLILITERS — ингредиент задан в миллилитрах
SERVINGS — ингредиент задан порциями продукта (например “4 яйца”)

2.3. Поля количества (в зависимости от measure_type)
Если measure_type = GRAMS

amount_g — количество в граммах (int > 0) обязательно
amount_ml = null
serving_id = null
servings_count = null

Если measure_type = MILLILITERS
amount_ml — количество в мл (int > 0) обязательно
amount_g = null
serving_id = null
servings_count = null

Если measure_type = SERVINGS

serving_id — ссылка на порцию продукта product_user_servings.id обязательно
(например “1 яйцо = 60 г” или “1 стакан = 250 мл”)
servings_count — сколько таких порций (float > 0) обязательно
(4 яйца, 1.5 ломтика и т.д.)
amount_g = null
amount_ml = null

Критически важные ограничения (логикой/констрейнтами):

В строке ингредиента разрешён только один способ задания количества.

serving_id должен принадлежать этому же продукту (product_user_id), иначе можно выбрать “порцию” от другого продукта.

4) Логика расчёта блюда (динамически, без хранения)

Расчёт делается при запросе блюда (например GET /dishes/:id).

4.1. Сначала нужно “разрешить” количество ингредиента до граммов

Поскольку КБЖУ на 100 г, всё сводим к grams.

Для каждой строки dish_items считаем resolved_grams:

A) GRAMS

resolved_grams = amount_g

B) SERVINGS

грузим serving по serving_id

если у порции weight_g:

resolved_grams = servings_count * serving.weight_g

если у порции volume_ml:

resolved_ml = servings_count * serving.volume_ml

resolved_grams = resolved_ml (считаем 1 мл = 1 г, issue: "Порция задана в мл, расчет приблизительный")

C) MILLILITERS

resolved_ml = amount_ml

resolved_grams = amount_ml (считаем 1 мл = 1 г)

4.2. Расчёт КБЖУ ингредиента

У продукта есть nutrition на 100г:

kcal_100, p_100, f_100, c_100 (+ опциональные)

Если resolved_grams известен:

коэффициент: k = resolved_grams / 100

kcal = kcal_100 * k

p = p_100 * k

f = f_100 * k

c = c_100 * k

и т.д. для сахара/клетчатки/соли

Если у продукта нет nutrition:

значения по ингредиенту null (или 0), и issue: “Нет КБЖУ у продукта”.

4.3. Расчёт цены ингредиента (последняя покупка)

Ты сказал: цена берётся по последней покупке у продукта.

Нужно правило “что такое последняя покупка”:

последняя по purchased_at, если есть

иначе по created_at

Покупка должна давать тебе “цена за единицу”:

Вариант 1 (самый простой и устойчивый)

Покупка хранит:

price_total

total_weight_g (или total_volume_ml)

Тогда:

если есть total_weight_g:

price_per_g = price_total / total_weight_g

ingredient_price = resolved_grams * price_per_g

если есть только total_volume_ml:

нужен resolved_ml или конверсия через density

price_per_ml = price_total / total_volume_ml

ingredient_price = resolved_ml * price_per_ml

Если покупки нет:

ingredient_price = null, issue: “Нет покупок — цена не посчитана”.

4.4. Итоги по блюду

Суммируем по всем ингредиентам, где данные посчитались:

total_kcal = Σ kcal

total_p = Σ p

total_f = Σ f

total_c = Σ c

total_price = Σ ingredient_price

Дальше “на порцию”:

per_portion_kcal = total_kcal / dishes.portions

аналогично для БЖУ

per_portion_price = total_price / dishes.portions

Если portions почему-то 0 — это ошибка данных, блюдо не должно сохраняться.

5) Что возвращать клиенту (чтобы было прозрачно)

Совет: возвращай блюдо + вычисления + список проблем.

Пример структуры ответа (идея, не схема):

dish: поля из dishes

items: как пользователь вводил (grams/ml/servings + serving info)

computed:

totals: kcal/p/f/c/price

perPortion: kcal/p/f/c/price

issues: массив объектов:

itemId

code (MISSING_NUTRITION, MISSING_PURCHASE, SERVING_INVALID, VOLUME_APPROXIMATION)

message

Так у тебя:

ничего не хранится в БД

данные всегда актуальные

фронт может подсветить, что надо дозаполнить

6) Предложения по улучшению (не ломая твою идею)
6.1. “Черновик блюда”

Добавь status в dishes (DRAFT/READY):

Тогда ты сможешь отдавать ещё:

Это сильно пригодится в будущем рационе.
